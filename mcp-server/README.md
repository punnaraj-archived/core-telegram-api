# Telegram Bot API MCP Server

An MCP server that exposes a focused subset of the Telegram Bot API while protecting agent-to-agent control traffic with end-to-end encryption.

## Security model

This server now uses two separate encryption boundaries:

1. **MCP transport E2EE** — every JSON-RPC frame on stdio is wrapped in a NaCl `box` envelope using Curve25519 key agreement, XSalsa20 encryption, and Poly1305 authentication.
2. **Telegram board payload E2EE** — `telegram_send_e2ee_message` encrypts the message body before it is submitted to Telegram. Telegram receives a versioned `RAOS-E2EE/1` ciphertext envelope rather than the agent plaintext.

Plaintext Telegram sending is **disabled by default**. The compatibility tool `telegram_send_message` is registered only when `ALLOW_PLAINTEXT_TELEGRAM_MESSAGES=true` is explicitly configured.

The two peers exchange public keys out-of-band. Each server instance is bound to exactly one configured peer public key. Secret keys are never sent on the wire.

## Security properties

- Confidentiality and authentication for MCP messages between the configured key pair.
- Confidentiality and authentication for Telegram board payloads between the configured key pair.
- Sender public-key pinning before decryption.
- Fresh random nonce per encrypted message.
- Bounded replay detection for recently accepted nonces.
- Strict Base64/key/nonce validation.
- Fail-closed rejection of plaintext or malformed MCP frames.
- 1 MiB encrypted MCP frame limit.
- Non-local Telegram Bot API endpoints must use HTTPS; local HTTP remains available for a self-hosted Bot API server on localhost.
- Telegram Bot API calls have bounded request timeouts and response-shape validation.
- HTTPS is required for configured webhook URLs.

### Explicit limitations

- Static long-lived NaCl key pairs do **not** provide forward secrecy. Rotate keys periodically and after suspected exposure.
- Replay detection is bounded in memory. Extremely old frames that have fallen outside the replay window cannot be recognized solely by this process instance.
- Telegram metadata such as chat identity, timing, and message size is not hidden by application-layer payload encryption.
- The Bot API token remains a separate credential and must be held in an environment secret or secret store.
- Production readiness still requires deployment-specific evidence: secret provisioning, process supervision, log policy, peer key distribution, rotation procedure, and end-to-end runtime verification.

## Setup

```sh
cd mcp-server
npm ci
npm run build
npm test
npm run keygen
```

Exchange **public keys only** with the intended peer through a trusted out-of-band channel.

Create `.env` from `.env.example` and configure:

- `TELEGRAM_BOT_API_URL` — `https://api.telegram.org` or a localhost self-hosted Bot API endpoint.
- `TELEGRAM_BOT_TOKEN` — bot token from BotFather.
- `MCP_LOCAL_SECRET_KEY` — this node's private key generated by `npm run keygen`.
- `MCP_PEER_PUBLIC_KEY` — the intended peer's public key.
- `ALLOW_PLAINTEXT_TELEGRAM_MESSAGES` — defaults to `false`; enable only as an explicit compatibility exception.

Start the MCP server:

```sh
npm start
```

## MCP tools

Default tools:

| Tool | Purpose |
| --- | --- |
| `telegram_get_me` | Read bot identity |
| `telegram_send_e2ee_message` | Encrypt a board message locally, then call Telegram `sendMessage` with ciphertext |
| `telegram_decrypt_e2ee_message` | Authenticate and decrypt an `RAOS-E2EE/1` board payload from the configured peer |
| `telegram_get_updates` | Poll Bot API updates |
| `telegram_get_chat` | Read chat information |
| `telegram_set_webhook` | Configure an HTTPS webhook |
| `telegram_delete_webhook` | Remove the webhook |

Compatibility-only tool when explicitly enabled:

| Tool | Purpose |
| --- | --- |
| `telegram_send_message` | Send plaintext Telegram text; bypasses board-level E2EE |

## Verification

`npm test` performs a TypeScript build and then runs Node's built-in test runner. Regression coverage includes:

- encrypted peer round-trip,
- duplicate-frame rejection,
- ciphertext modification rejection,
- wrong-peer rejection,
- malformed Base64 rejection,
- Telegram board ciphertext round-trip,
- plaintext board payload rejection,
- oversized encrypted board payload rejection.

GitHub Actions also runs build, E2EE regression tests for `mcp-server`, and `npm audit --audit-level=moderate` on pull requests affecting MCP packages.

## Operational recommendation

Treat each agent/node as a separate cryptographic identity. Do not reuse one private key across all nodes. Keep the Telegram board as a communication surface, not as the trust root: peer keys and local policy remain the authority boundary.
